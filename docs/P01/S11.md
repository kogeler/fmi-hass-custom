## Objective

Prove and document collision-safe, idempotent migration of v0.6.2 config entries and registries while preserving entity/device identity, customized IDs, multi-entry isolation, and post-migration reconfiguration behavior.

## Changes made

- Added a compact synthetic v0.6.2 fixture containing two complete config entries, coordinate identities, device records, core and optional entities, generated suffixes, and customized IDs.
- Added Home Assistant-level acceptance coverage for config-only and setup-time registry migration, repeated migration/reload, config and entity target collisions, same-place multi-entry histories, duplicate coordinates, future-version refusal, reconfiguration, and daily option disable/re-enable.
- Documented the stable identity, collision, ambiguous suffix, location-device, and optional daily entity policies in `docs/maintenance/MIGRATIONS.md` and aligned the existing sensor, forecast, and reconfiguration references.
- Updated the maintenance matrix, decision log, and changelog with the significant completed migration guarantees.

## Root causes and decisions

- v0.6.2 tied config/device/entity identity to coordinates. Version 2 keeps the original coordinate identity only as immutable compatibility data while moving config-entry uniqueness to `fmi:<entry_id>`, so later coordinate changes reuse existing registries.
- Current entity-registry records cannot prove whether `_2` was allocated automatically or selected later by a user. Migration therefore renames only exact unsuffixed defaults when the target is free and preserves every ambiguous, customized, or occupied ID.
- Home Assistant cannot generally rewrite dashboard and automation references when an entity disappears. The optional daily weather registry entry is retained as unavailable while disabled and reattached unchanged when enabled.
