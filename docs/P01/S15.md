## Root causes and decisions

- The owner-provided untracked `.version` is preserved as intentional input and starts the release line at `1.0.0`.
- The repository's actual default branch is `master`; all new PR and release gates target it.
- Current HACS guidance confirms that the standard `custom_components/fmi/` layout is native and that a published GitHub Release, not a tag alone, supplies HACS's remote version.
- GitHub release publication will use full-SHA-pinned `actions/github-script` and its pre-authenticated client. CI will not use `curl`, `gh api`, or a custom HTTP client for GitHub API calls.
- Every repository-authored CI helper will be Python under `.github/scripts/`; no root `scripts/` directory or custom shell/JavaScript helper file will be added.
- `.version` is the only human-edited version. The manifest is a committed generated mirror; PR and push workflows compare two checked-out trees so the helper does not depend on Git inside the Python image.
- The release workflow is concurrency-safe and idempotent: an existing release is accepted only when its tag, target, title, notes, and published state match exactly; conflicts are rejected without mutation.
- Compatibility runs automatically and manually. It resolves current stable and prerelease channels without committed HA/helper/runtime release pins, freezes and recreates each selected graph, blocks on stable failures, and treats prerelease failures as informational. Bounded live probes are a required PR/release gate after offline coverage.
- Stable compatibility is an event-driven PR signal as well as a manual check. Prerelease runs on the same events but remains non-blocking because it is an unsupported moving target; release publication does not become manually triggerable.
- The supported stable development/test graph remains one complete committed freeze; pip bootstrap and moving compatibility graphs are separate environments, and every automated pip installation consumes requirement/constraint files rather than inline packages or versions.
- An external FMI or network outage is intentionally release-blocking under the owner-selected live-CI policy; the documented failure classification and one manual rerun distinguish service outages from contract regressions.
- GitHub cannot reject a direct `master` commit retroactively after a post-push failure. Required PR checks and owner-configured branch protection are the preventive control.
- PR-body writes require `pull_request_target` for fork support. The sole exception has no secrets, checks out only the trusted default branch, reads the head changelog through GitHub's API as bounded data, and grants no repository-content write permission.
- The first `1.0.0` PR cannot run the new updater while `pr-body.yml` is absent from `master`; GitHub loads `pull_request_target` workflows only from the default branch. Later PRs activate it automatically on open, reopen, and source updates.
- Standalone CI, validation, and version checks intentionally repeat on a `master` release push: the Release workflow must invoke its own exact-SHA gates because independent workflow runs cannot be referenced with cross-workflow `needs`.
- The base of the first release has neither `.version` nor the current integration layout: version fallback must read root `manifest.json` before comparing `1.0.0` with legacy `0.6.2`.
- GitHub's dependency-diff REST endpoint returns `403` for fork repositories. The workflow therefore uses native dependency review only when the repository is independent and otherwise audits the complete committed freeze against exact package/version/advisory exceptions; new and stale findings are both blocking.
- The three CodeQL alerts were valid, not false positives: the unmaintained debug-only lightning script logged coordinate-derived values and request URLs and had no runtime/test ownership, so deletion was safer than suppression or partial redaction.
