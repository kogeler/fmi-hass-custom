## Objective

Make forecast and observation availability independent enough that a forecast WFS incident does not disable usable current observations, with explicit setup, stale-data, recovery, lifecycle, and logging behavior.

## Changes made

- Added `CHANGELOG.md` with the significant S00-S04 maintenance, compatibility, security, and availability outcomes; added the per-session notable-change rule to the maintenance plan.
- Initialized the forecast-backed and configured-station coordinators independently and enter setup retry only when no current-condition source initializes.
- Added place-observation fallback for coordinate-current failures so issue #117 keeps current weather and sensors available without inventing forecast data.
- Clear failed or timed-out current/forecast results, represent an unavailable forecast as empty, and restore data automatically on later successful refreshes.
- Isolated lightning and sea-level exceptions from core current availability and moved optional work outside the primary timeout boundary.
- Removed duplicate manual coordinator listeners and the coordinator's duplicate data notification; coordinator entity lifecycle now owns registration and cleanup.
- Added transition-only source outage/recovery logging and reduced repeated per-entity no-data messages to debug level.
- Added ten offline availability, setup/retry, stale-data, recovery, logging, optional-source, timeout, and unload/reload tests plus the installed client contract for `async_observation_by_place`.
- Documented the complete availability policy in `docs/maintenance/AVAILABILITY.md` and corrected the plan's inaccurate claim that S02 had created a #117 strict `xfail`.

## Root causes and decisions

- Setup refreshed the forecast coordinator first and aborted before a configured station could contribute usable observations; a configured station failure also made a healthy primary coordinator fatal. The first refreshes now run independently and setup succeeds when either current-condition path works.
- The coordinate-current API can fail with the same forecast WFS incident as the forecast collection. The config-entry title is the FMI-resolved place name, so `async_observation_by_place(title)` is the bounded fallback specified by #117.
- Failed forecast calls left the previous collection attached to the coordinator. Current and forecast values are now cleared when freshness cannot be guaranteed rather than exposed as current.
- Entities manually registered callbacks in addition to `CoordinatorEntity` registration, while `_async_update_data` also invoked `async_set_updated_data` before returning data to `DataUpdateCoordinator`. Removing both duplicate paths produces one lifecycle-managed update per entity and clean unload.
- Lightning and sea-level are optional data. Their exception boundary clears only the affected optional attribute; detailed parsing/transport/freshness behavior remains in S09.
