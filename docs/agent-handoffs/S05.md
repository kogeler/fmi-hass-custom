## Objective

Make hourly and daily forecasts semantically correct, deterministic, timezone-aware, compatible with Home Assistant's current weather forecast contract, and robust to missing or unordered FMI samples while fixing incorrect daily forecast regression.

## Changes made

- Replaced the first-sample daily forecast shortcut with deterministic local-calendar aggregation for temperature, precipitation, condition, wind, pressure, humidity, cloud coverage, and dew point.
- Preserved a complete one-hour FMI source series so daily `Precipitation1h` totals remain complete when the legacy presentation interval is coarser; retained downsampling only for existing non-weather consumers.
- Added normalized, chronological hourly forecasts and timezone-aware daily forecasts using Home Assistant's current native forecast keys and UTC RFC 3339 timestamps.
- Removed the deprecated `forecast` property, made the primary weather entities advertise literal hourly and daily methods, and disabled forecast features on observation-only weather entities.
- Retained the optional legacy daily entity and its unique ID until S11 can prove a registry-safe migration or retirement path.
- Added explicit finite/missing-value handling, last-sample-wins timestamp deduplication, and millimetre normalization for the FMI client's one-hour precipitation unit.
- Added a deterministic forecast fixture corpus and regression coverage for incorrect daily forecast regression, mixed conditions, partial days, DST boundaries, duplicate/unordered samples, missing and negative values, units, feature flags, and Home Assistant forecast subscriptions.
- Documented the source and aggregation contract in `docs/maintenance/FORECAST_SEMANTICS.md`, updated the notable changelog, and corrected the maintenance plan as source-contract and migration constraints were verified.
- Resolved all four inherited `weather.py` mypy errors without casts or ignores, reducing the tracked repository baseline from 18 errors in four production files to 14 errors in three.

## Root causes and decisions

- The old daily implementation selected the first sample of each day and only updated temperature extremes. That made precipitation and every other daily field dependent on payload order instead of aggregating the source values.
- FMI `Precipitation1h` describes an individual preceding-hour amount, while the client returns values only for requested timesteps. Querying at a configured three-hour interval therefore discards values required for a valid daily total; the coordinator now requests one-hour samples once and reuses them for both granularities.
- Daily grouping uses Home Assistant's configured timezone and the full local date, including DST transitions. The exposed daily timestamp is local midnight converted to UTC, satisfying both local-day semantics and Home Assistant's UTC contract.
- Daily condition uses a documented deterministic severity order instead of the first hour. Sustained wind uses the daily maximum and its bearing; pressure, humidity, cloud coverage, and dew point use finite-value means. Partial days are included without extrapolation.
- Removing the duplicate legacy daily entity immediately could orphan an existing customized unique ID. S11 owns the registry migration decision; S05 makes the retained entity's advertised methods correct in the meantime.
