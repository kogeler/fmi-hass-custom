## Objective

Allow an existing FMI config entry to change coordinates through Home Assistant's reconfigure flow without losing entity identity, customized entity IDs, or working data when validation fails.

## Changes made

- Added the current Home Assistant `reconfigure` config-flow step with existing coordinates as defaults, translated connection/unknown errors, duplicate-location rejection, FMI validation before mutation, resolved-place title updates, and reload through the entry's existing update listener.
- Replaced config-entry version 1's coordinate-bound identity with version 2's immutable `entity_identity`. Fresh entries receive coordinate-independent identities; legacy entries retain their exact original `latitude:longitude` entity/device identity while their config unique ID moves to `fmi:<entry_id>` when collision-free.
- Updated coordinators, and therefore device/weather/sensor unique IDs, to use immutable identity instead of current coordinates. Moving an entry now updates its data and display context without recreating entities or changing customized IDs.
- Added 13 config-flow/migration regressions covering setup identity, the location reconfiguration requirement flow, invalid coordinates, FMI/malformed-response failures, cancellation, duplicates, v0.6.2 migration, config-ID collision, one reload, place-name updates, and registry identity preservation.

## Root causes and decisions

- location reconfiguration requirement could not be fixed by simply updating latitude/longitude: the original integration derived the config-entry, device, weather, and sensor identities from those coordinates, so a move would orphan registry identity and automation references.
- Version 2 stores identity separately. Legacy `entity_identity` deliberately remains the original colon-separated coordinate string so existing unique IDs are byte-for-byte unchanged; fresh entries use a random stable ID that has no location semantics.
- Duplicate detection now compares current coordinates because immutable config IDs no longer describe location. It excludes the entry being reconfigured and checks again after asynchronous validation in the initial user flow.
- A config-unique-ID migration collision retains the legacy config ID rather than overwriting another entry. Entity identity is still migrated safely and stays immutable.
- The flow uses `async_update_and_abort`, relying on the loaded entry's existing update listener for one affected-entry reload. Using `async_update_reload_and_abort` as well would schedule a second reload when the listener is present in current Home Assistant.
- Dynamic Home zone tracking was rejected for this effort: manual reconfigure fully resolves the location reconfiguration requirement without adding a coordinate subscription and another identity/migration lifecycle.
- Home Assistant tests use xdist processes rather than shared threads so worker event loops and process-global integration state stay isolated. Two and four workers were retained as opt-in because warm-container measurements showed 49-53% slower wall time than one process on the current 82-item collection.
